## What It Does

The `log-to/` Pulumi program creates a Logto Deployment, persistent volume claim, API Service, admin Service, and API Ingress. It expects PostgreSQL to already exist in the same Kubernetes namespace.

The repository currently includes `dev` and `experiments` Logto stack examples, but no `Pulumi.dcr-kube1.yaml` or other production Logto stack file. Treat production installation as **configuration work first, deployment second**. Do not apply a lab stack against production.

## Version and Image

The latest release shown by the official Logto repository during this update is **v1.43.0**:

| Setting | Production value | Reason |
|---|---|---|
| Image | `svhd/logto` | Image name used by this repository's Pulumi program |
| Tag | `1.43.0` | Immutable pin for the current official latest release |
| API port | `3001` | Logto core API |
| Admin port | `3002` | Logto admin service |

Do not use `svhd/logto:latest`. Update the pinned tag only after reviewing the release notes and completing a database backup.

Logto v1.43.0 release notes require database alterations before the new version starts. The current container command attempts seed, alteration deployment, connector linking, and application startup in that order. Confirm migration completion in the pod logs after every version change.

## Prerequisites

| Requirement | Check | Notes |
|---|---|---|
| Production cluster shell | `echo "$PULUMI_STACK"` | Run inside `just cluster-env --env prod --cluster <prod-cluster>` |
| Kubernetes access | `kubectl config current-context` | Must target intended production cluster |
| PostgreSQL operator and cluster | `just postgres verify` | Cluster name `logto`, namespace `prod`. Installed by [`postgres-deploy.md`](../../postgres-deploy.md), never from the Logto guide |
| PostgreSQL application Secret | `kubectl -n prod get secret logto-app` | Contains username and password keys |
| PostgreSQL write Service | `kubectl -n prod get service logto-rw` | Logto uses Kubernetes service environment variables |
| Production Logto config | `test -f log-to/Pulumi.<production-stack>.yaml` | Not present in the repository today; add and review before apply |

PostgreSQL must be installed first. The Logto Deployment reads `logto-app` and resolves `logto-rw` during pod startup.

## PostgreSQL Connection

The current Pulumi program sets these container variables:

| Variable | Source | Value |
|---|---|---|
| `DBUSER` | Secret `logto-app`, key `username` | PostgreSQL application role, normally `logto` |
| `PGPASSWORD` | Secret `logto-app`, key `password` | PostgreSQL application password |
| `DB_URL` | Kubernetes service discovery | `postgresql://$(DBUSER)@$(LOGTO_RW_SERVICE_HOST):$(LOGTO_RW_SERVICE_PORT)/logto?sslmode=no-verify` |
| `ENDPOINT` | Pulumi config | Public Logto endpoint |
| `TRUST_PROXY_HEADER` | Pulumi program | `1` behind the repository's ingress proxy |

`LOGTO_RW_SERVICE_HOST` and `LOGTO_RW_SERVICE_PORT` are generated by Kubernetes for Service `logto-rw`. Keep PostgreSQL and Logto in namespace `prod`; otherwise those service variables will not point at the intended database.

`sslmode=no-verify` matches the current in-cluster implementation. Do not reuse this connection string outside the cluster without reviewing TLS requirements.

## Production Configuration

Create `log-to/Pulumi.<production-stack>.yaml` using this shape. Replace domain, TLS secret, and ingress host values with production values. Store sensitive values through Pulumi's configured secrets provider; do not commit plaintext credentials or private hostnames.

```yaml
config:
  log-to:properties:
    name: logto
    namespace: prod
    databaseSecret: logto-app
    storageClass: dictycr-balanced
    diskSize: 50Gi
    endpoint: https://<logto-auth-domain>
    image:
      name: svhd/logto
      tag: 1.43.0
    apiPort: 3001
    adminPort: 3002
    ingress:
      tlsSecret: <logto-tls-secret>
      backendHosts:
        - <logto-auth-domain>
      label:
        name: kcert.dev/ingress
        value: managed
```

The current program routes the Ingress to `logto-api` only. It creates `logto-admin` as a separate internal Service and does not expose that Service through the Ingress. Confirm intended admin-console access before production apply.

Before applying:

1. Confirm PostgreSQL created `logto-app` and `logto-rw` in `prod`.
2. Confirm the image tag is `1.43.0`, not `latest`.
3. Confirm `endpoint`, TLS secret, and host are production values.
4. Run `just gcp-pulumi preview --folder log-to` and inspect every resource change.

## Deployment

Run from inside the production cluster shell. `create-resource` runs `pulumi up -f -y` — it does not prompt, so the preview is the only review point:

```bash
just gcp-pulumi preview --folder log-to
just gcp-pulumi create-resource --folder log-to
```

The first apply creates PVC `logto-claim` and Deployment `logto`, then Services `logto-api` and `logto-admin`, then Ingress `logto-ingress`. The container then runs its database seed and alteration commands before starting Logto. A failed migration leaves the rollout unhealthy; inspect logs before retrying.

For later upgrades, update only the image tag, preview, apply, and verify migration logs before routing traffic to the new pod.

## Verification

Run these checks after apply:

```bash
kubectl -n prod rollout status deployment/logto
kubectl -n prod get pods -l app=logto
kubectl -n prod get svc/logto-api svc/logto-admin ingress/logto-ingress
kubectl -n prod logs deployment/logto --tail=200
```

Success criteria:

- Deployment has an available ready pod.
- Pod logs show database seed/alteration completion and Logto startup without errors.
- `logto-api` Service has an endpoint.
- API Ingress has the expected production host and TLS configuration.
- Logto endpoint responds through the production hostname.

## Troubleshooting

| Symptom | Cause | Action |
|---|---|---|
| `secret "logto-app" not found` | PostgreSQL cluster was not deployed in `prod`, or config uses wrong Secret name | Run `just postgres verify`; set `databaseSecret: logto-app` |
| `LOGTO_RW_SERVICE_HOST` is empty | Service is missing or Logto runs in another namespace | Check `kubectl -n prod get service logto-rw`; keep both workloads in `prod` |
| Pod fails during database alteration | Image migration failed or database is not reachable | Read pod logs, verify `logto-app`, then check PostgreSQL status before retrying |
| Image pull fails | Registry tag is wrong or cluster lacks registry access | Verify `svhd/logto:1.43.0` and image-pull permissions |
| API works but admin console is unreachable | Current Pulumi program exposes Ingress only for API Service | Add an approved admin exposure design; do not point API Ingress at the admin port |
| Preview targets lab resources | Wrong Pulumi stack or production config absent | Stop; return to the production `cluster-env` shell and inspect `pulumi stack` |
